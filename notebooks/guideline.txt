## 1. TECHNOLOGY STACK

- **Primary Language**: Python 3.11+
- **API Framework**: FastAPI
- **ORM**: SQLAlchemy 2.0 with async support
- **Database (Production)**: PostgreSQL 15+
- **Database (Development/Testing)**: SQLite
- **Authentication**: JWT (JSON Web Tokens) using python-jose
- **Password Hashing**: bcrypt via passlib
- **Validation**: Pydantic v2
- **API Documentation**: OpenAPI 3.0 (auto-generated by FastAPI)
- **Testing Framework**: pytest with httpx (TestClient)
- **Containerization**: Docker with multi-stage builds
- **Container Orchestration**: Kubernetes (K8s)
- **CI/CD Pipeline**: GitHub Actions
- **Code Quality**: black, isort, flake8, mypy

## 2. PROJECT STRUCTURE

## 3. API DESIGN STANDARDS

### 3.1 URL Convention
- Use lowercase with hyphens: `/api/v1/user-profiles`
- Always version APIs: `/api/v1/...`
- Use plural nouns for resources: `/users`, `/orders`
- Nested resources for relationships: `/users/{id}/orders`

### 3.2 HTTP Methods
- GET: Retrieve resources (never modify state)
- POST: Create new resources
- PUT: Full update of a resource
- PATCH: Partial update of a resource
- DELETE: Remove a resource

### 3.3 Response Format
All responses MUST follow this envelope format:
```json
{
    "success": true,
    "message": "Operation completed successfully",
    "data": { ... },
    "meta": {
        "page": 1,
        "per_page": 20,
        "total": 100
    }
}
```

### 3.4 Error Response Format
```json
{
    "success": false,
    "message": "Validation error",
    "errors": [
        {
            "field": "email",
            "message": "Invalid email format"
        }
    ]
}
```

### 3.5 Status Codes
- 200: Successful GET, PUT, PATCH
- 201: Successful POST (resource created)
- 204: Successful DELETE
- 400: Bad request / Validation error
- 401: Unauthorized
- 403: Forbidden
- 404: Resource not found
- 409: Conflict (duplicate resource)
- 422: Unprocessable entity
- 500: Internal server error

## 4. AUTHENTICATION & AUTHORIZATION

### 4.1 JWT Configuration
- Access token expiry: 30 minutes
- Refresh token expiry: 7 days
- Algorithm: HS256
- Token must be sent in Authorization header: `Bearer <token>`

### 4.2 Required Auth Endpoints
- POST `/api/v1/auth/register` - User registration
- POST `/api/v1/auth/login` - User login (returns JWT)
- POST `/api/v1/auth/refresh` - Refresh access token
- POST `/api/v1/auth/logout` - Invalidate token

### 4.3 Role-Based Access Control
- Implement role-based middleware
- Default roles: admin, user, viewer
- Protect endpoints with dependency injection

## 5. DATABASE STANDARDS

### 5.1 Model Requirements
- All models MUST have: id (UUID), created_at, updated_at
- Use UUIDs as primary keys (not auto-increment integers)
- Soft delete pattern: add `is_deleted` and `deleted_at` fields
- Index frequently queried columns

### 5.2 Naming Conventions
- Table names: snake_case, plural (e.g., `user_profiles`)
- Column names: snake_case (e.g., `first_name`)
- Foreign keys: `<table_singular>_id` (e.g., `user_id`)

## 6. TESTING STANDARDS

### 6.1 Test Requirements
- Minimum 80% code coverage
- All endpoints must have happy path and error path tests
- Use fixtures for test data
- Tests must be independent and idempotent

### 6.2 Test Categories
- Unit tests for services/business logic
- Integration tests for API endpoints
- Database tests with test fixtures

## 7. DEVOPS STANDARDS

### 7.1 Docker
- Use multi-stage builds
- Base image: python:3.11-slim
- Non-root user in production
- Health check endpoint: GET `/health`

### 7.2 Kubernetes
- Resource limits must be defined
- Liveness and readiness probes required
- ConfigMaps for non-sensitive configuration
- Secrets for sensitive data
- Horizontal Pod Autoscaler (HPA) configuration

### 7.3 CI/CD Pipeline
- Lint and format check
- Run all tests
- Build Docker image
- Push to container registry
- Deploy to staging
- Manual approval for production

## 8. LOGGING & MONITORING

- Use structured JSON logging
- Log levels: DEBUG, INFO, WARNING, ERROR, CRITICAL
- Include correlation ID in all logs
- Log all API requests and responses (sanitize sensitive data)

## 9. SECURITY REQUIREMENTS

- Input validation on all endpoints
- SQL injection prevention (use ORM parameterized queries)
- Rate limiting on auth endpoints
- CORS configuration (restrict origins in production)
- No secrets in code or logs
- HTTPS only in production

## 10. DOCUMENTATION

- All endpoints must have OpenAPI descriptions
- Include request/response examples
- Document error scenarios
- README must include setup instructions, architecture diagram, and API overview
