## 1. CONTAINERISATION (DOCKER)

### 1.1 Dockerfile Standards
- Use multi-stage builds for smaller images
- Base image: `python:3.11-slim`
- Run as non-root user in production
- Copy `requirements.txt` first for layer caching
- Health check: `HEALTHCHECK CMD curl -f http://localhost:8000/health || exit 1`
- Expose port 8000

### 1.2 Example Multi-Stage Dockerfile
```dockerfile
# Stage 1: Build
FROM python:3.11-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# Stage 2: Runtime
FROM python:3.11-slim
WORKDIR /app
RUN adduser --disabled-password --no-create-home appuser
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
USER appuser
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=10s CMD curl -f http://localhost:8000/health || exit 1
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 1.3 docker-compose.yml
- Service for the API application
- For SQLite: single service with volume mount
- For PostgreSQL: add `db` service with health check
- Environment variables via `.env` file
- Port mapping: `8000:8000`

### 1.4 .dockerignore
Must exclude: `.git`, `__pycache__`, `*.pyc`, `.env`, `venv/`, `myenv/`,
`.pytest_cache`, `node_modules`, `.idea`, `.vscode`

## 2. KUBERNETES (K8s)

### 2.1 Required Manifests
- `k8s/deployment.yaml` — Deployment with resource limits and probes
- `k8s/service.yaml` — ClusterIP service on port 80 → container 8000
- `k8s/configmap.yaml` — Non-sensitive config (APP_NAME, LOG_LEVEL, etc.)
- `k8s/hpa.yaml` — HorizontalPodAutoscaler

### 2.2 Deployment Standards
- `replicas: 2` minimum for HA
- Resource limits:
  - requests: `cpu: 100m`, `memory: 128Mi`
  - limits: `cpu: 500m`, `memory: 512Mi`
- Liveness probe: `GET /health`, `initialDelaySeconds: 10`
- Readiness probe: `GET /health`, `initialDelaySeconds: 5`
- Image pull policy: `IfNotPresent`
- Labels: `app`, `version`, `environment`
- Environment from ConfigMap and Secrets

### 2.3 Service Standards
- Type: `ClusterIP` (use Ingress for external access)
- Port: 80 → targetPort: 8000
- Selector must match deployment labels

### 2.4 HPA Configuration
- Min replicas: 2
- Max replicas: 10
- Target CPU utilization: 70%
- Scale-down stabilization: 300 seconds

## 3. CI/CD PIPELINE (GitHub Actions)

### 3.1 Workflow File
Location: `.github/workflows/ci-cd.yml`

### 3.2 Pipeline Stages
1. **Lint & Format** — Run `flake8`, `black --check`, `isort --check`
2. **Test** — Run `pytest -v --tb=short`, fail pipeline on test failure
3. **Build** — Build Docker image, tag with commit SHA and `latest`
4. **Push** — Push image to GitHub Container Registry (ghcr.io)
5. **Deploy Staging** — Auto-deploy to staging environment
6. **Deploy Production** — Manual approval gate

### 3.3 Workflow Triggers
- `push` to `main` branch
- `pull_request` to `main` branch

### 3.4 Environment Variables & Secrets
- Use GitHub Secrets for: `OPENAI_API_KEY`, `DATABASE_URL`, `JWT_SECRET`
- Use workflow `env:` for: `PYTHON_VERSION`, `REGISTRY`

## 4. GIT & PR STANDARDS

### 4.1 Branch Naming
- Feature branches: `feature/<project-name>-stub`
- Sanitise names: replace spaces with hyphens, remove special chars
- Always branch from `main`

### 4.2 Commit Messages
- Format: `feat: <project-name> — AI-generated API stub`
- Include context about what was generated

### 4.3 Pull Request Standards
- Title: `feat: <project-name> — AI-generated API stub`
- Body MUST include:
  - Auto-generated disclaimer
  - The API specification (JSON)
  - List of generated files
  - Build log summary
- Target branch: `main`
- Assign reviewers if configured

### 4.4 PR Automation
- The DevOps agent is responsible for:
  1. Initialising a git repo in the output directory
  2. Creating a feature branch
  3. Committing all generated artefacts
  4. Pushing to the remote GitHub repository
  5. Creating a pull request via the GitHub API

## 5. DEPLOYMENT STANDARDS

### 5.1 Environment Configuration
- Dev: SQLite, debug mode, localhost
- Staging: PostgreSQL, no debug, internal URL
- Production: PostgreSQL, no debug, HTTPS, rate limiting

### 5.2 Health Check
- Endpoint: `GET /health`
- Must return: `{"status": "healthy", "version": "1.0.0"}`
- Used by Docker HEALTHCHECK and K8s probes

### 5.3 Secrets Management
- Never commit secrets to version control
- Use environment variables for all sensitive config
- Use Kubernetes Secrets or GitHub Secrets in CI/CD
- Rotate secrets regularly

## 6. MONITORING & LOGGING

- Structured JSON logs
- Log levels: DEBUG (dev), INFO (staging), WARNING (prod)
- Include correlation ID in logs
- Prometheus metrics endpoint (optional)
- Alert on: high error rate, high latency, pod restarts

## 7. SECURITY CHECKLIST (DEPLOYMENT)

- [ ] No secrets in Dockerfile or docker-compose.yml
- [ ] Non-root user in container
- [ ] Read-only filesystem where possible
- [ ] Network policies in Kubernetes
- [ ] TLS termination at ingress/load balancer
- [ ] Container image scanning enabled
- [ ] Dependency vulnerability scanning in CI/CD
